## Access and accounts

Both tools use the existing `endepth_teachers` identity and ownership registry. Existing Morgan and Teacher 2 IDs, ownership, stored credentials, and assignment slugs are preserved. The administrator uses the existing administrator code for the first sign-in, then a stored scrypt hash; teachers' existing salted legacy hashes upgrade to scrypt after successful sign-in. Environment teacher codes are never an automatic recovery path. Rotating or disabling an account revokes its sessions and old credential. Administrator code rotation also revokes the administrator's sessions and permanently stops the old environment administrator code from authenticating.

From the department portal, Morgan signs in with the existing administrator credential and selects **Add approved roster**. The seven exact approved emails are added idempotently, with the email itself as a placeholder display name and **awaiting activation** state. An existing case-insensitive email match keeps its ID and credential; duplicate existing matches require reconciliation rather than guessing. No full names are inferred. Existing approved accounts retain their current state. Morgan can edit verified display names inside the app.

**Activate & issue individual code** generates a 256-bit random code and stores a salted scrypt hash. It activates an awaiting account and shows the code only in the authenticated administrator response/UI. Copy it immediately and deliver it privately to that teacher using an existing approved channel. Active accounts instead show a collapsed **Replace active teacher code** control, with a distinct action that replaces the credential and revokes sessions. Preserve those existing credentials during rollout. This application does not send invitation emails and does not contain a public credential directory. One teacher credential opens both module desks. **Disable** revokes access; **Reactivate & issue new code** is the explicit administrator reactivation action. Teachers cannot create staff accounts, change roles, or take ownership of someone else's assignment.

Staff sessions use hashed, revocable server-side session tokens, eight-hour expiry, and `HttpOnly; Secure; SameSite=Strict` cookies. Staff credentials are not retained in browser storage. JSON mutations require an exact matching Origin and reject cross-site requests. Login, coaching, credential issuance, invitation creation, and sandbox creation/reset use database-backed rate limits. Preview and production should use separate databases: cookies can be host-specific while a shared database still exposes the same records.

## Teacher workflow

1. Sign in at the department entry with the individual credential. Use **EnDepth Teacher Desk** for the existing assignment and submission workflow. Existing student links, named submissions, Draft/Open/Closed behavior, seventeen-student admission, four successful exchanges, rich diagnostic feedback, moderation and `store:false` remain.
2. In **EnScribe Writing Studio**, create a draft assignment with course, section, prompt, instructions, optional teacher rubric, timing and boundaries. Open it when ready; close it to reject student workspace actions. Duplicate creates a new draft and does not transfer existing student work. No school rubric is invented. Focus categories are labeled thesis/inquiry, structure, evidence, analysis and grammar/usage/mechanics. All settings prohibit rewriting; Restrictive disables coaching on the server.
3. Open **Students / import / access links**. Enter each student's separate identity fields and optionally paste the independently written original, including manually exported Exam.net writing. Generate that student's private access link and deliver it privately. This is paste/import, not Exam.net or Google Classroom integration. Replacing a private student link revokes the old capability without changing the original or revisions.
4. Review original, working/final draft, revisions and explanations, reflection, successful checks, coaching history and actual submission status. CSV export escapes quotes/newlines and spreadsheet formula prefixes. **Reopen** permits more revisions but does not reset coaching quota or original. A stalled EnScribe check older than five minutes can be released for that student's assignment; stale completions cannot finalize a newer retry lease.
5. **Try EnScribe** and **Try EnDepth** create clearly marked fictional assignments owned by the signed-in teacher, separate from live student work. Testing uses the real, bounded coach endpoints when configured; it never silently substitutes simulation after a live failure. EnScribe resets apply only to the teacher's own sandbox rows. New tests and resets are rate limited. EnDepth testing uses the teacher's session, not disclosure of the class pilot code.

Students save their independent original before requesting EnScribe coaching. A database trigger prohibits changing it afterward. Later saves require an expected version and revision explanation. Concurrent/stale saves return a conflict; the UI keeps unsaved text so the writer can copy and reconcile it before loading the server version. Saving does not submit. Submission requires reflection and returns real server confirmation; the teacher must reopen submitted work. EnScribe students authenticate by a private random capability, never by email alone. Tokens are hashed in the database, exchanged for an HttpOnly cookie, and removed from the browser URL fragment without being saved in browser storage. An EnScribe invitation is not a public shared assignment.

Academic input construction explicitly excludes identity metadata, credentials and invitation tokens. Live checks send academic writing to OpenAI, using input/output moderation and `store:false`. Free-text writing itself may contain identifying details. Coaching returns diagnostics, a revision strategy and a focused question; it must not generate replacement prose, thesis, evidence, citations, paragraphs or outlines. Provider failures and withheld feedback do not consume successful checks. EnScribe reservation/finalization is atomic and lease-aware; duplicate completed requests return cached feedback. EnDepth now has a persistent request ledger preserving existing successful-count rows and preventing duplicate retries from consuming extra exchanges. Pending reservations fail closed; do not reset quotas to recover provider errors.

## Rollback and incident handling

The new EnScribe module can be temporarily disabled with the server variable `DEPARTMENT_WRITING_DISABLED=1`. This rejects its staff/student actions while preserving all saved writing. Keep the shared security upgrade and existing EnDepth routes active. Prefer a forward fix; do not blindly redeploy the old teacher-code recovery implementation, which can restore revoked credentials and reactivate disabled accounts. If code must be rolled back, preserve the cookie-session, hash-upgrade and recovery-removal changes.

Do not drop the new tables, remove columns, restore old credential hashes, reset successful coaching counts, replace existing assignment slugs or restore student originals from a deployment snapshot. SQL migration is additive and retained during code rollback. Disable affected accounts inside the authenticated administrator interface and rotate credentials deliberately. Investigate stale EnDepth reservations without blindly clearing in-flight counts: only request-ledger entries identified as abandoned may be released, and old pending operations must be made unable to finalize a replacement lease. EnScribe exposes this recovery for its owned student records. Test cleanup must target only synthetic IDs created by that test, never broad production deletes.
